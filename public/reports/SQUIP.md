# SQUIP (CVE-2021-46778) 实验报告

## 1. 本项目具体说明

SQUIP（Scheduler Queue Usage via Interference Probing，CVE-2021-46778）是一种利用现代超标量处理器分离式调度器队列设计缺陷的侧信道攻击。本项目通过构建 Sender（受害/干扰端）与 Receiver（探测端）双程序 PoC，复现同一物理核心 SMT 线程间的调度器队列争用，并观察延迟放大现象。

## 2. 涉及资源

- **分离式调度器队列（Scheduler Queues）**
  - **位置**: AMD Zen 2/3/4 后端执行与调度路径。
  - **功能**: 不同执行单元使用独立队列（如乘法单元队列）。
  - **利用**: 两个 SMT 线程共享这些队列，攻击者可通过队列填充造成争用。

- **SMT（Simultaneous Multithreading）共享资源**
  - **位置**: 同一物理核心的两个逻辑线程。
  - **功能**: 共享后端部分执行与调度资源。
  - **利用**: Sender 与 Receiver 分别运行在同核两个 SMT 线程，形成可观测干扰。

- **高延迟浮点指令与依赖桥**
  - **位置**: Receiver 关键汇编序列。
  - **功能**: `sqrtsd` 构造延迟窗口，`cvtsd2si` 建立浮点到整数寄存器依赖。
  - **利用**: 迫使后续 `imulq` 在队列内排队，放大争用效应。

- **时间测量原语**
  - **位置**: `rdtscp` 计时路径。
  - **功能**: 周期级测量指令窗口耗时。
  - **利用**: 比较 Sender 关闭/开启时 Receiver 的平均延迟差异。

## 3. 攻击原理

攻击核心是“队列填充 + 排队探测”模式：

1. Sender 在死循环中持续执行 `imulq`，占用乘法相关调度资源。
2. Receiver 先用多条 `sqrtsd` 构造观测窗口，再通过 `cvtsd2si` 建立强依赖。
3. Receiver 插入固定数量 `imulq`，并记录执行周期（Cycles）。
4. 对比 Sender OFF（Baseline）与 Sender ON（Attack）时的延迟曲线，判断是否出现队列拥堵尖峰。

## 4. 项目核心代码文件

- **`receiver.c`**: 探测端主程序，负责构造观测窗口并测量 `N_MULS` 扫描区间延迟。
- **`sender.c`**: 干扰端主程序，持续执行乘法指令占用调度器资源。
- **`复现报告.md`**: 实验环境、原理与结果记录文档。

## 5. 运行环境

- **物理处理器（Host CPU）**: AMD Ryzen 7 7840H（Zen 4，8 核 16 线程）
- **宿主机系统（Host OS）**: Windows 11
- **虚拟机软件**: VMware Workstation
- **虚拟机系统（Guest OS）**: Ubuntu 24.04 Desktop
- **关键配置**:
  - 虚拟机配置为 1 个处理器，2 个内核（Total cores: 2）。
  - 宿主机端强制绑定 CPU 亲和性，确保虚拟机 vCPU 运行在同一物理核心的两个 SMT 线程上。

## 6. PoC 设计

### 6.1 Receiver（探测端）

Receiver 使用 Prime+Probe 思路测量调度器队列拥塞：

1. 使用 `sqrtsd` 形成长延迟路障，防止指令过快退休。
2. 使用 `cvtsd2si` 建立依赖桥，强制后续 `imulq` 在队列中等待。
3. 扫描不同 `N_MULS`，统计对应平均延迟。

### 6.2 Sender（受害/干扰端）

Sender 通过死循环持续执行乘法指令，模拟高强度运算场景，长期占用乘法相关调度资源，制造跨 SMT 线程争用压力。

## 7. 验证结果

### 7.1 数据对比

选取关键乘法填充数量的延迟对比：

| 乘法填充数（N） | 基准延迟（Sender OFF） | 攻击延迟（Sender ON） | 延迟增幅 | 判定结果 |
| --- | ---: | ---: | ---: | --- |
| **19** | 237 | **542** | **+128%** | **显著拥堵** |
| **25** | 262 | **1105** | **+321%** | **极端拥堵** |
| **29** | 281 | **751** | **+167%** | **显著拥堵** |
| **38** | 322 | **492** | **+52%** | **拥堵** |

### 7.2 结果分析

1. **基准线（Baseline）**: 无干扰时延迟随 N 增长而平滑上升，整体保持较低水平（<350 cycles）。
2. **攻击线（Attack）**: Sender 开启后，在特定 N 点位出现剧烈延迟尖峰。
3. **代表性点**: `N=25` 达到 `1105 cycles`，表明 Receiver 插入乘法指令时遭遇明显队列饱和与分发停顿。
4. **随机性说明**: 尖峰并非连续出现，可能受虚拟机调度中断与系统噪声影响。
